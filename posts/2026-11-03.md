## **约定式提交（Conventional Commits）** 规范

### 一、核心格式
~~~text
<类型>[(作用域)][!]: <描述>

[可选正文]

[可选脚注]
~~~
- **类型**：必填，见下方清单

- **作用域**：可选，括号内写影响范围，如模块名 `auth`、`api`

- `!`：可选，表示破坏性变更

- **描述**：必填，简短说明，建议 ≤50 字符，动词开头，不加句号

- **正文**：可选，说明“为什么改”，与描述空一行

- **脚注**：可选，关联 Issue 或写 `BREAKING CHANGE`:
### 二、常用类型清单
| 类型 | 含义 | 示例 |
| --- | --- | --- |
| feat | 新功能 | feat: 增加手机号登录 |
| fix | 修复 Bug | fix: 修复订单金额计算错误 |
| docs | 仅文档变更 | docs: 更新接口说明 |
| style | 格式调整（空格、分号、缩进，不影响逻辑） | style: 统一缩进为2空格 |
| refactor | 重构（既非新功能也非修 Bug） | refactor: 抽取公共请求方法 |
| perf | 性能优化 | perf: 减少列表重复渲染 |
| test | 增删改测试 | test: 补充登录单元测试 |
| build | 构建系统或依赖变更 | build: 升级 webpack 到 5 |
| ci | CI 配置变更 | ci: 增加 PR 自动检查 |
| chore | 杂务（不修改源码和测试的琐事） | chore: 更新 .gitignore |
| revert | 回滚某次提交 | revert: 回滚 feat: 增加手机号登录 |
> 记忆技巧：**功能用 feat，修错用 fix，文档 docs，格式 style，重构 refactor，性能 perf，测试 test，构建 build，流水线 ci，杂事 chore。**

### 三、作用域怎么用
作用域用来标明改动落在哪个模块，便于筛选和定位。
~~~text
fix(auth): 修复 token 过期未刷新
feat(order): 支持批量导出订单
docs(api): 补充分页参数说明
~~~
作用域不是必填，小项目可以省略；模块多、多人协作时建议加上，并与团队约定好命名（如 auth、order、user）。
### 四、描述怎么写
- 用**动词开头**：增加、修复、调整、删除、抽取、替换

- 说清**做了什么**，不写“修改代码”“更新一下”这类空话

- 不加句号，控制长度

- 中文或英文均可，团队统一即可

| 不推荐 | 推荐 |
| --- | --- |
| `fix: 改了一下` | `fix: 修复分页参数越界导致空列表` |
| `feat: 新功能` | `feat: 支持按标签筛选文章` |
| `update` | `refactor: 将日期格式化抽为工具函数` |

### 五、正文与脚注
改动简单时一行描述足够；改动复杂时，正文说明动机和影响。
~~~text
fix(payment): 修复退款金额少算优惠券

退款时未扣除已使用的优惠券金额，导致多退。
改为先计算实际支付金额再发起退款。

Closes #128
~~~
破坏性变更要显式标注，两种写法任选：
~~~text
feat(api)!: 移除 v1 接口

BREAKING CHANGE: /api/v1/users 已删除，请迁移到 /api/v2/users
~~~
或
~~~text
feat!: 重构配置加载方式

BREAKING CHANGE: 配置文件由 config.js 改为 config.json
~~~
### 六、完整示例合集
~~~text
feat: 增加手机号验证码登录
fix(cart): 修复删除商品后总价未更新
docs: 补充本地启动步骤
style: 格式化 user 模块代码
refactor(utils): 将请求封装拆分为独立文件
perf(list): 使用虚拟滚动优化长列表
test(auth): 补充登录失败用例
build: 升级 Node 版本要求到 18
ci: 增加提交信息格式校验
chore: 删除无用图片资源
revert: 回滚 "feat: 增加手机号验证码登录"
~~~
### 七、落地工具
1. **交互式填写：**安装 `commitizen`，用 `git cz` 代替 `git commit`，按提示选择类型、填作用域和描述，自动拼出规范信息。

2. **提交时校验：**`commitlint` + `husky`，在 `commit-msg` 钩子里检查格式，不合规直接拦截，保证仓库历史一致。

3. **自动生成日志：**`conventional-changelog` 按类型生成 `CHANGELOG`。

4. **自动发版：**`semantic-release` 根据 `fix`/`feat`/`BREAKING CHANGE` 自动决定补丁、次版本、主版本号。

### 八、一张速查卡
~~~text
text
格式：<类型>(作用域): 描述

类型：feat fix docs style refactor perf test build ci chore revert

描述：动词开头 + 说清做了什么 + 不加句号 + 尽量短

破坏性变更：类型后加 !，脚注写 BREAKING CHANGE: 说明

关联 Issue：脚注写 Closes #编号
~~~
