## 了解git

![alt text](images/git.png)

#### Git 是一个开源的分布式版本控制系统，用于敏捷高效地处理任何或小或大的项目。
1. **版本控制系统**

版本控制系统（VCS）就是**记录文件每次修改历史的工具**。比如你写文档，改了十版，它能帮你记住每一版改了什么、谁改的、什么时候改的，还能随时回到某一版。Git 就是干这个的，只不过它主要管代码。

2. **分布式**

关键在于**和「集中式」对比**。集中式版本控制系统（如 SVN）是这样的：
~~~ txt
        [中央服务器]  ← 唯一的完整历史仓库
         /    |    \
      开发者A 开发者B 开发者C   ← 本地只有当前版本的文件
~~~
- 完整的历史记录**只存在中央服务器**上

- 每个人本地只有一份"当前版本"的文件

- 提交、查历史、回滚都要**联网连服务器**

- 服务器挂了，所有人都没法干活；服务器数据丢了，历史就没了

而 Git 是**分布式**的
~~~ txt
   [远程仓库]（GitHub/GitLab 等，只是个"副本"）
      ↕        ↕        ↕
   开发者A   开发者B   开发者C
   （本地都有完整的仓库和历史）
~~~
- 每个人 clone 下来时，本地就有一份完整的仓库，包含全部历史记录

- 提交、查历史、切分支、回滚，全在本地完成，不需要联网

- 远程仓库（如 GitHub）本质上只是众多副本中的一个，不是"唯一权威"

- 服务器挂了，你本地照样能工作，历史一条不少

#### Git 是 Linus Torvalds 为了帮助管理 Linux 内核开发而开发的一个开放源码的版本控制软件。

1. **Linus Torvalds 是谁**

Linux 内核的创始人。1991 年他写出 Linux 内核，后来全世界大量开发者参与贡献代码——人一多，就需要一个工具来管理"谁改了什么、怎么合并"，这就是版本控制系统的需求。

2. **为什么他要"自己开发"**

背景：Linux 内核早期用的是 BitKeeper（一个商业的集中式版本控制系统），当时免费给开源项目用。2005 年，因为授权纠纷，Linux 社区不能再免费用 BitKeeper 了。

Linus 面临两个选择：

- 找一个现成的替代品 → 当时没有满足他要求的

- 自己写一个 → 他选了这条

他对新工具有几个硬性要求：

- 快（Linux 内核巨大，提交频繁）

- 分布式（每个开发者本地有完整历史）

- 强力支持分支和合并（大量开发者并行贡献）

- 能防数据损坏（用 SHA-1 哈希校验内容完整性）

结果他只花了两周左右就写出了 Git 的第一个可用版本，2005 年 4 月发布。这个"为了管理 Linux 内核而生"的背景，正好解释了 Git 为什么是分布式、为什么快、为什么分支这么轻量——都是被 Linux 内核这种超大规模协作场景逼出来的。

1. **"开放源码"的含义**

Git 是开源软件，意味着：

- 源代码公开，任何人都能看、能改、能分发

- 免费使用，不受商业授权限制

- 这也是它后来能取代 BitKeeper、成为业界标准的重要原因之一

## git 入门

1. 创建新仓库
创建新文件夹，打开，然后执行`git init`
2. 检出仓库
~~~ bash
#执行如下命令以创建一个本地仓库的克隆版本：
git clone /path/to/repository
#如果是远端服务器上的仓库，你的命令会是这个样子：
git clone username@host:/path/to/repository
~~~
- `/path/to/repository` 是源仓库的位置（从哪克隆）

- `git clone` 执行后，会在当前目录下新建一个文件夹（默认用源仓库名命名），里面就是克隆出来的仓库——这才是你本地得到的副本

3. 工作流
你的本地仓库由 git 维护的三棵“树”组成。第一个是你的 `工作目录`，它持有实际文件；第二个是 `暂存区（Index）`，它像个缓存区域，临时保存你的改动；最后是 `HEAD`，它指向你最后一次提交的结果。

![alt text](images\git-guide-trees.png)

   1. **工作目录（Working Directory）**
   就是你打开文件夹看到的**实际文件**。你在这里编辑、增删文件。Git 会对比它和暂存区/HEAD 的差异，告诉你"哪些文件被改了"（`git status` 就是干这个的）。
   2. **暂存区（Index / Staging Area）**
   一个**中间缓冲区**。你 `git add` 的文件会进到这里，表示"这些改动我打算放进下一次提交"。它的存在让你能**挑选**：改了 5 个文件，可以只把其中 2 个 `add` 进去提交，另外 3 个先不提交。这就是"缓存区域"的含义。
   3. **HEAD**
   一个**指针**，指向你当前所在分支的**最后一次提交**。它代表"已经提交保存的版本"。`git commit` 后 HEAD 就前移到新提交上。

文件的生命周期就是在这三处之间移动：
  1. 你**新建/修改**文件 → 变化发生在**工作目录**
  2. `git add` → 把改动**放进暂存区**
  3. `git commit` → 把暂存区的内容**固化成一次提交**，HEAD 随之指向这个新提交

#### 根据树的概念看命令的本质

| 命令 | 作用（用三棵树解释） | 补充说明 |
|---|---|---|
| `git status` | 对比工作目录、暂存区、HEAD，告诉你差异 | 只读操作，不改任何东西；常用 `git status -s` 看精简版 |
| `git add <file>` | 工作目录 → 暂存区 | `git add .` 暂存当前目录所有改动；`git add -p` 可交互式逐块挑选 |
| `git commit` | 暂存区 → 本地仓库，HEAD 前移 | `git commit -m "msg"` 直接写说明；`git commit -am "msg"` 跳过 add（仅对已跟踪文件有效） |
| `git diff` | 工作目录 vs 暂存区 | 看"改了但还没 add"的内容 |
| `git diff --staged` | 暂存区 vs HEAD | 看"已 add 但还没 commit"的内容；等价于 `git diff --cached` |
| `git diff HEAD` | 工作目录 vs HEAD | 看"所有未提交的改动"（已 add + 未 add 合在一起） |
| `git checkout -- <file>` | 用暂存区/HEAD 的内容覆盖工作目录（丢弃改动） | 危险：未暂存的改动会永久丢失，无法恢复；新版 Git 推荐用 `git restore <file>` |
| `git reset <file>` | 把文件从暂存区撤出（暂存区 → 工作目录方向） | 只撤销 add，不动工作目录里的实际内容；新版 Git 推荐用 `git restore --staged <file>` |
| `git reset --hard HEAD` | 工作目录、暂存区、HEAD 全部对齐到最后一次提交 | 危险：丢弃所有未提交改动，慎用 |
| `git rm <file>` | 删除文件并同时从工作目录和暂存区移除 | 相当于 `rm` + `git add`；`git rm --cached <file>` 只从版本控制移除、保留本地文件 |
| `git mv <old> <new>` | 重命名/移动文件，并同步更新暂存区 | 相当于 `mv` + `git add` 新旧路径 |
